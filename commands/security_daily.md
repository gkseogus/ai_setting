오늘 기준 최신 보안 이슈를 내 프로젝트와 대조해 영향 여부를 판정하고, 노션 보안 문서에 음슴체 데일리 보고서로 남긴다.

## 인자
$ARGUMENTS — 모두 선택사항. 자유 텍스트로 받는다.
- **대상**: 점검할 프로젝트. 아래 중 아무거나, 여러 개 줄 수 있다. 비어 있으면 현재 디렉터리의 레포.
    - 레포 경로
    - 레포가 모여 있는 디렉터리 (그 아래 git 레포 전부)
    - 서비스 이름 (현재 디렉터리나 그 부모 디렉터리에서 그 이름으로 시작하는 레포 묶음. 프론트·백엔드·어드민·인프라처럼 레포가 나뉜 서비스를 한 번에 볼 때)
- **기간**: 예) `최근 3일`, `2026-11-20 이후`. 비어 있으면 대상별 직전 기록 날짜부터 오늘까지 (작업 순서 2번).
- **계기**: 공지 URL, CVE 번호, 들은 이야기 등. 주면 그 이슈를 가장 먼저 확인하고 보고서 `계기` 에 적는다.
- 예시: `/security_daily`, `/security_daily shop CVE-2026-12345`, `/security_daily ~/projects 최근 3일`

## 어디에 쓰는가
사용자의 노션 워크스페이스에는 보안 보고서를 모아 두는 `보안 문서` 페이지가 있다. 그 바로 아래에 하루 한 페이지를 만든다.
```
보안 문서
├── (기존 감사·점검 보고서들)
└── 보안 데일리 점검 보고서 (YYYY-MM-DD)   ← 오늘 페이지
```
같은 날 다시 돌리면 새 페이지를 만들지 않고 오늘 페이지를 갱신한다 (작업 순서 6번).

## 대상

- 특정 프로젝트 전용이 아니다. 인자로 받은 프로젝트(없으면 현재 레포)가 대상이고, 그 프로젝트가 무엇을 쓰는지는 실행할 때 레포에서 읽는다.
- 프로젝트 이름·버전·스택·서버 구성을 이 파일에 적어 두지 않는다. 매번 레포와 운영에서 직접 읽는다.
- **패치 절차 문서**: 대상 레포(인프라 레포가 있으면 그쪽)의 README·`docs/` 에 보안 패치나 배포 절차가 있으면, 조치할 때 그것을 따른다.

### 판정 용어 (이 다섯 가지만 쓴다)

| 판정 | 언제 | 뒤에 붙일 근거 |
| --- | --- | --- |
| **영향 있음** | 실측 버전이 영향 범위이고, 취약한 부분이 운영에서 실제로 돌고 있으며, 로그인 없이(또는 누구나 가입할 수 있는 계정으로) 악용될 수 있음 | 실측 버전, 수정 기준 버전, 밖에서 닿는 경로가 있는지 |
| **영향 가능** | 영향 범위이고 실제로 돌고 있지만, 악용 조건이 성립하는지 확정하지 못함 | 실측 버전, 무엇을 확정하지 못했는지 |
| 낮음 | 영향 범위이지만 해당 기능을 쓰지 않거나, 관리자·내부 계정으로만 악용할 수 있거나, 빌드 때만 쓰임 | 그렇게 본 근거(코드 검색 결과, 접근 제한) |
| 해당 없음 | 쓰지 않는 소프트웨어이거나 이미 수정 버전 이상 | 실측 버전 또는 "사용 안 함" |
| 확인 못 함 | 버전이나 사용 여부를 읽지 못함 | 왜 못 읽었는지. `7. 남은 과제` 에도 넣음 |

- **밖에서 직접 닿지 않는다는 이유만으로 `낮음` 으로 내리지 않는다** — 접근 제한은 근거에 적고, 얼마나 급한지(당일 / 예약)를 정할 때만 쓴다. 내부 서버의 커널 결함처럼 접근 제한이 있어도 패치해야 하는 것을 놓치지 않기 위함.
- 취약점 등급(치명·높음·중간·낮음)은 `이슈` 칸 괄호 안에만, 판정은 `판정` 칸에만 적는다.

## 말투 규칙
- **음슴체 고정** — "확인함", "올림", "남아 있었음", "해당 없음" 등 `~함/~음` 어미.
- **비개발자도 이해할 수 있게** — 취약점은 CVE 번호만 적지 말고 "무엇을 당할 수 있는지"를 한 구절로 푼다. 예: "조작된 요청으로 서버를 멈추거나 코드를 실행할 수 있음".
- **숫자로 적는다** — "많이 줄었음" 이 아니라 "27 → 23". 서비스가 끊겼으면 시각과 초 단위 길이를 적는다.
- **이모지 금지**.

## 작업 순서

1. 오늘 날짜를 구하고 (`date +%Y-%m-%d`, KST 기준), 인자에서 대상 레포 목록을 정해 사용자에게 보여 준다.
   - 다음 경우에는 진행하기 전에 `AskUserQuestion` 으로 확인한다: 서비스 이름에 서로 다른 서비스로 보이는 레포가 함께 걸렸을 때, 인자의 낱말이 대상인지 계기인지 애매할 때, 대상을 비웠는데 현재 디렉터리가 git 레포가 아닐 때.
   - 답을 받을 수 없는 실행(예약 실행 등)이면 애매한 대상은 빼고 진행하고, 뺀 사실을 보고서 머리말 `참고` 에 적는다.
2. 직전 기록을 읽는다.
   - `notion-search` 로 "보안 문서" 페이지를 찾아 `notion-fetch` 로 자식 목록을 본다.
   - 가장 최근 `보안 데일리 점검 보고서` 를 읽는다. 데일리가 하나도 없으면 날짜가 가장 최근인 점검·대응 보고서를 읽는다 (같은 날짜가 여러 개면 전부).
   - **검색 시작일은 대상마다 따로 정한다** = 그 대상이 머리말 `대상` 에 들어 있던 가장 최근 기록의 날짜(그날 포함). 위에서 읽은 기록에 그 대상이 없으면 최근 30일의 기록을 최근 것부터 거슬러 찾고, 그래도 없으면 30일 전. 인자로 기간을 받았으면 그것을 쓴다. (전체 공통으로 잡으면, 어제 다른 프로젝트만 점검했을 때 이 프로젝트의 그 전 기간이 통째로 빠짐)
   - **이월 목록** = 가장 최근 기록의 `남은 과제` 전체(다른 프로젝트 것 포함). 이 중 오늘 대상의 항목이면서 다음 확인일이 오늘이거나, 지났거나, 비어 있는 것은 이번에 다시 확인한다. 오늘 대상이 아닌 프로젝트의 항목은 다시 확인하지 않고 그대로 옮긴다.
   - 오늘 페이지가 이미 있으면 6번에서 새로 만들지 않고 갱신한다.
3. 내 환경을 실측한다 (읽기 전용).
   - 레포마다 `git fetch origin` 을 먼저 한다 (원격 정보만 갱신되고 작업 트리는 그대로임). 운영에 올라간 브랜치(보통 `main`, 아래에서는 `<운영 브랜치>`) 기준으로 읽는다.
   - `git checkout`·`switch`·`stash`·`pull` 로 작업 트리를 바꾸지 않는다. 작업 트리가 운영 브랜치가 아니거나 `origin/<운영 브랜치>` 보다 뒤처져 있으면 `git show origin/<운영 브랜치>:<파일>` 로 필요한 파일을 임시 폴더에 꺼내, 거기서 읽고 감사 도구도 거기서 돌린다.

   대상 레포에 해당 파일이나 자원이 있는 줄만 본다.

   | 무엇을 | 있을 때 | 어떻게 |
   | --- | --- | --- |
   | JS 의존성 | `package.json` | 잠금 파일의 프레임워크·주요 패키지 버전, `npm audit --omit=dev` 와 `npm audit` 로 운영·개발 구분 (yarn·pnpm 이면 그 도구의 audit) |
   | Python 의존성 | `requirements*.txt`·`pyproject.toml` | 의존성·잠금 파일, `pip-audit`. 도구가 없으면 OSV 조회로 대신함 |
   | 그 밖의 언어 | 그 언어의 잠금 파일 | 그 생태계의 감사 도구. 없으면 OSV 조회 |
   | 컨테이너 이미지 | `Dockerfile*` | 베이스 이미지 태그·digest, 이미지에 넣는 런타임·도구 버전, 이미지 저장소의 취약점 스캔 결과 |
   | 서버·DB | 인프라 코드나 클라우드 자원 | 인프라 코드의 OS 이미지·DB 엔진 버전, 클라우드의 읽기 전용 조회 명령(`describe-*`·`list-*` 등)으로 실제 버전과 대기 중인 유지보수 |
   | 관리형 호스팅 | Vercel 등에 배포 | 런타임 버전 (예: `vercel project inspect <프로젝트> --scope <스코프>`. 스코프가 여러 개면 전부) |
   | CI | 워크플로 파일 | 런타임 버전 지정, 기간 안의 워크플로 파일 변경 여부 |

   - 시크릿 값을 읽는 조회는 하지 않는다 (`secretsmanager get-secret-value`, `ssm get-parameter --with-decryption` 등).
   - 레포 안에 파일을 만들거나 바꾸는 명령은 쓰지 않는다 (`npm install`, `vercel link`, `vercel pull` 등).
   - 서버 안에서 명령을 돌려야 알 수 있는 값(커널 버전 등)은 실행 전에 사용자 동의를 받는다.
   - 자격 증명이나 도구가 없어 못 본 것은 건너뛰고 `확인 못 함` 으로 판정한다.
4. 대상별 검색 시작일 이후에 나온 보안 이슈를 `WebSearch` 로 찾는다. 3번에서 실제로 쓰는 것으로 확인된 소프트웨어를 기준으로 검색한다.

   | 영역 | 출처 |
   | --- | --- |
   | 서버 OS·커널 | 쓰는 배포판의 보안 공지 (예: Amazon Linux Security Center, Ubuntu Security Notices), 클라우드 사업자 보안 공지 |
   | 컨테이너 베이스 | 베이스 이미지 배포판의 보안 추적기 (예: Debian Security Tracker) |
   | 런타임 | 쓰는 언어 런타임의 보안 릴리스 공지 (예: Node.js, Python) |
   | 프레임워크·라이브러리 | GitHub Advisory Database 를 실측에서 나온 패키지 이름으로 조회 |
   | DB | 쓰는 DB 의 보안 릴리스 공지. 관리형이면 사업자가 제공하는 버전도 |
   | 브라우저 | Chrome 릴리스 (이미지나 서버에 브라우저가 있을 때) |
   | 공급망 | 패키지 저장소의 악성 패키지 배포, CI 서비스 침해 소식 |
   | 실제 공격 | CISA 실제 공격 목록(KEV) |
   | 국내 공지 | KISA 보호나라 |

   - 크게 보도된 이슈는 내가 쓰지 않는 소프트웨어여도 `해당 없음` 한 줄로 남긴다 (나중에 "그건 봤나?"에 답하기 위함).
5. 이슈마다 영향을 판정한다. 아래 순서대로 묻고, 답이 정해지는 곳에서 멈춘다. 이월 목록에서 다시 확인하기로 한 항목도 같은 방식으로 본다.
   1. 실측 버전이 영향 범위 안인가 → 아니면 `해당 없음`
   2. 취약한 부분이 운영에서 실제로 도는가 (그 기능을 코드에서 쓰는가, 빌드 때만 쓰이는가) → 아니면 `낮음`
   3. 로그인 없이, 또는 누구나 가입할 수 있는 계정으로 악용되는가 → 관리자·내부 계정으로만 가능하면 `낮음`, 가능하면 `영향 있음`, 확정하지 못하면 `영향 가능`
   - 버전이나 사용 여부를 읽지 못해 1·2에 답할 수 없으면 `확인 못 함`.
6. 위 양식으로 보고서를 기록한다.
   - 오늘 페이지가 없으면 `보안 문서` 아래에 `보안 데일리 점검 보고서 (YYYY-MM-DD)` 를 만든다.
   - 있으면 그 페이지를 갱신한다: 머리말 `대상` 에 이번 대상을 더하고, `1` 절 표에 새 행을 더하고, `0. 한 줄 요약` 과 `7. 남은 과제` 표를 지금 상태로 고친다. 이미 적힌 판정 행과 근거 문장은 지우지 않는다.
   - `7. 남은 과제` 에는 네 가지를 넣는다.
     - 이월 목록 중 아직 끝나지 않은 항목 전부 (확인일이 아직 오지 않은 것도 그대로 옮김 — 옮기지 않으면 다음 날 기록에서 사라짐)
     - 오늘 `확인 못 함` 으로 판정한 항목
     - 수정본이 있는데 오늘 조치하지 않은 항목
     - 영향 범위인데 수정본이 아직 나오지 않은 항목 (상태에 "수정본 대기"로 적음 — 넣지 않으면 수정본이 나와도 다시 보지 않게 됨)
   - `7. 남은 과제` 의 항목 앞에는 프로젝트 이름을 적는다 (다른 날 다른 프로젝트의 항목과 섞여 이월되므로). 대상이 여러 개면 `1` 절의 판정 근거에도 어느 프로젝트 것인지 적는다.
   - 다음 확인일은 따로 정해진 날짜가 없으면 7일 뒤로 적는다.
   - 이월 목록에서 끝난 항목은 상태를 "완료"로 적어 오늘 페이지에 한 번 남기고, 다음 날부터 뺀다.
7. 오늘 대상에서 조치할 수 있는 항목을 모은다: 수정본이 있는데 적용되지 않은 항목, 그리고 수정본은 없지만 우회 조치(설정 변경, 기능 끄기, 접근 제한)가 있는 `영향 있음`·`영향 가능` 항목. 하나도 없으면 이 단계를 건너뛰고 8번으로 간다. 있으면 `영향 있음` → `영향 가능` → `낮음` 순으로 조치안(바꿀 것, 예상 중단 시간, 되돌리는 방법)을 보여 주고 `AskUserQuestion` 으로 **어느 항목을 조치할지, Jira 에픽을 만들지** 승인받는다. 승인된 항목만 진행하고, 고르지 않은 항목은 `7. 남은 과제` 에 둔다.
   - 사용자가 미룬 항목은 다음 확인일이 올 때까지 다시 묻지 않는다.
   - 답을 받을 수 없는 실행(예약 실행 등)이면 조치하지 않고 조치안을 `7. 남은 과제` 에 적는다.
   - 코드·의존성 변경은 해당 레포에서 브랜치를 만들어 PR 로 올린다.
   - PR 머지, 운영 배포, 서버 재부팅, DB 변경, 운영 설정 변경(우회 조치 포함), 백업(서버 이미지·스냅샷) 삭제는 각각 실행 직전에 다시 동의를 받는다.
   - 인프라 코드로 관리하는 설정 중 패치 절차 문서에 없는 변경(우회 조치 등)은 콘솔·CLI 로 바로 바꾸지 않고 인프라 레포 PR 로 바꾼다 (바로 바꾸면 다음 적용 때 조용히 되돌아감).
   - 서버·DB 변경은 대상 레포에 패치 절차 문서가 있으면 그대로 따르고, 없으면 조치안에 적어 승인받은 순서대로 한다. 어느 쪽이든 백업을 먼저 만든다.
   - 에픽을 만들기로 했으면 `/jira_project` 를 쓴다.
   - 배포 뒤 3번의 실측을 운영에서 다시 하고, `/final_test` 로 운영 최종 테스트를 돌린다.
   - 오늘 페이지에 `조치 현황`·`2`·`3`·`4`·`4-1`·`5` 를 채우고, `0. 한 줄 요약` 과 `1` 절의 조치 칸을 고친다.
8. 사용자에게 페이지 URL 과 판정 결과(영향 있음 n건, 영향 가능 n건, 확인 못 함 n건, 남은 과제 n건)를 알려준다. 조치를 했으면 `/notion_diary` 로 일지에 남길지, `/slack_share 보안` 으로 공지 글을 만들지 묻고, 일지에 남겼으면 `참고` 절에 일지 페이지 멘션을 더한다.

## 주의사항
- **점검은 읽기 전용** — 7번에서 승인받기 전에는 레포 파일, 운영 서버, DB, 클라우드 설정을 바꾸지 않는다.
- **추정과 실측을 구분한다** — 버전은 파일이나 명령 출력에서 읽은 값만 적는다. 못 읽었으면 `확인 못 함` 이다.
- **"수정본이 나왔다"는 배포판 추적기에서 수정 버전을 확인한 뒤에만 적는다** — 올릴 새 버전이 있다는 것만으로는 그 취약점이 고쳐졌다고 볼 수 없다.
- **자원은 대상 서비스 것만 센다** — 대기 중인 유지보수나 스캔 결과를 계정 전체 조회 결과 그대로 합치지 않는다.
- **이미지 스캔 결과가 비어 보이면 조회 대상을 의심한다** — 여러 아키텍처용으로 만든 이미지는 결과가 태그가 붙은 인덱스가 아니라 아키텍처별 이미지에 붙는 저장소가 있다. "결과 없음"으로 적기 전에 확인한다.
- **자동 수정이 다운그레이드를 제안하면 받지 않는다** — `npm audit fix --force` 는 쓰지 않는다.
- **틀린 보고는 지우지 않는다** — 앞서 적은 내용이 틀린 것을 알게 되면 `6. 점검 중 정정한 내용` 에 무엇이 틀렸고 실제는 무엇인지 남긴다.
- **다른 페이지는 건드리지 않는다** — `보안 문서` 의 다른 보고서는 읽기만 한다. 오늘 페이지도 통째로 새로 쓰지 않고 6번 방식으로 고친다.
- **자동 commit 금지** — 사용자가 명시적으로 요청하지 않는 한 이 저장소에도, 점검 대상 레포에도 커밋·푸시하지 않는다 (7번에서 승인받은 PR 은 예외).
- **운영의 약점은 노션 보고서에만 적는다** — 미패치 상태, 열린 포트, 자원 ID 같은 내용을 공개 저장소의 파일·커밋 메시지·PR 본문에 옮겨 적지 않는다.
