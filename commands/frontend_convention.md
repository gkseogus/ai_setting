## 컨벤션 파일
@/Users/hdh/Desktop/ai_setting/template/frontend_conventions.md

## 작업 순서
1. 위 컨벤션 파일을 읽고 내용을 숙지합니다.
2. 현재 프로젝트의 src/ 디렉토리를 탐색합니다.
3. 컨벤션 위반 사항을 찾아 리스트업합니다.
4. 사용자에게 위반 사항을 보여주고 수정 여부를 확인합니다.
5. 승인된 항목에 대해 수정을 진행합니다.

## 주요 검사 항목
- 컴포넌트가 기능 단위로 그룹핑되고 `contents/`·`types/`가 컴포넌트와 분리되어 있는지 (폴더 구조)
- 상수(라벨 맵·옵션 배열·색상·설명 텍스트)가 `src/contents/`에 분리되어 있는지
- 화살표 함수 규칙을 따르는지 (컴포넌트·유틸·핸들러는 화살표, Next.js 페이지 export는 function 허용)
- useEffect 위치가 return 바로 위인지 (인라인 컴포넌트가 있으면 그 위)
- import가 `@/` 절대경로를 사용하는지 (`../` 상대경로 금지)
- 타입 네이밍이 Face/Type 접미사를 따르는지
- 상수가 UPPER_SNAKE_CASE인지
- 1파일 1컴포넌트 원칙을 따르는지 (인라인 컴포넌트는 같은 디렉터리로 분리)
- 커스텀 훅이 `use` 접두사 네이밍·단일 책임·반환 타입 명시·`"use client"` 지시어를 지키는지
- 에러/로딩/빈 상태 UI가 있는지 (로딩은 스켈레톤 우선, 에러는 비기술 메시지+재시도)
- Tailwind 클래스 순서 및 cn() 사용 여부
- 인라인 `style`은 동적 값에만 쓰고, 반응형은 모바일 퍼스트(sm→md→lg)인지
- API 호출 함수가 `src/api/`에 관심사별로 분리되어 있는지
- 모든 API 호출이 React Query(`useQuery`/`useMutation`) 훅으로 감싸져 있는지
- React Query 키가 `src/api/keys.ts`에 중앙 관리되는지 (인라인 키 사용 금지)
- 컴포넌트에서 직접 `fetch`/`axios` 호출하지 않는지
- 코드 변경 시 관련 문서(README, .env.example, 컴포넌트/훅 문서, API 연동 문서)가 같은 작업 단위에서 갱신되었는지
- 기능 추가/수정 시 관련 테스트(컴포넌트/훅은 같은 폴더 `*.test.ts(x)`, E2E는 `e2e/*.spec.ts`)가 같은 커밋 범위에 추가·갱신되었는지 (버그 수정은 회귀 테스트 필수)
- 테스트가 `.skip`/`xit`로 비활성화된 채 커밋되지 않았는지 (부득이하면 사유 주석 명시)
