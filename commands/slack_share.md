작업 내용이나 배포 결과를 슬랙 채널에 올릴 공유 글로 다듬어 **추천 텍스트**를 만든다. 슬랙에 직접 보내지 않는다.

## 인자
$ARGUMENTS — 모두 선택사항. 자유 텍스트로 받는다.
- **유형**: `배포` / `공지` / `결과` / `보안`. 비어 있으면 아래 "유형 고르기" 기준으로 추정한다.
- **채널**: 예) `#98_펫시어지`. 주면 그 채널의 내 최근 글로 톤·멘션을 맞춘다.
- **내용 범위**: 예) `오늘 커밋`, `PR #42`, 직접 적은 메모. 비어 있으면 현재 세션 작업 + 오늘 커밋을 대상으로 한다.

## 유형 고르기

| 유형 | 언제 | 채널 |
|------|------|------|
| `배포` | 기능 추가·수정을 운영에 올렸고 담당자 확인이 필요할 때 (기본값) | 프로젝트 채널 |
| `공지` | 전사에 알릴 새 도구·전체 영향 변경·보안 안내(정책, 주의 당부). 점검·패치 결과는 `보안` | 전사 채널 (`@channel`) |
| `결과` | 검증·분석 결과나 결정이 필요한 논의를 대표님께 공유할 때 | 기존 스레드 답글 |
| `보안` | 보안 점검·패치 결과를 알릴 때. "보안 공지" 요청도 점검·패치 결과면 여기 (`/security_daily` 나 보안 점검 보고서가 재료) | `#보안-점검` (프로젝트마다 글 하나, 전용 양식) |

## 작업 순서

1. **재료 모으기** — 추측으로 채우지 않는다.
   - 현재 세션에서 한 작업, `git log --since=midnight --pretty='%h %s'`(범위 인자가 있으면 그 범위), PR 이 있으면 `gh pr view <번호>` 본문.
   - 배포 여부·URL·수치(건수, 전후 값, 시간)는 세션·커밋·PR 에서 확인된 것만 쓴다.
   - `보안` 은 노션 `보안 문서` 아래의 해당 보고서(인자로 URL·날짜를 주면 그것, 없으면 오늘 날짜 보고서)를 `notion-fetch` 로 읽어 재료로 쓴다. 같은 날짜 보고서가 여러 개면 프로젝트별 보고서를 그 프로젝트 글의 재료로 쓰고, 데일리 하나뿐이면 그 안에서 프로젝트별로 나눈다. 보고서에 없는 수치는 쓰지 않는다.
2. **톤 맞추기** (채널을 알 때만. `보안` 은 하지 않음 — 양식이 고정이라 이전 글의 섹션을 따르지 않는다) — `slack_search_public_and_private` 로 `from:<@내ID> in:<#채널> 배포` 를 최신순 2건 읽고, 멘션 대상·첫 문장·섹션 이름을 그대로 따른다. 멘션 대상은 저장소에 적지 않고 매번 여기서 가져온다.
3. **유형별 양식으로 작성** — 아래 양식과 말투 규칙을 따른다.
4. **출력** — 추천 텍스트를 ```markdown 코드블록으로 준다(글 하나당 블록 하나). 블록 안은 슬랙 입력창에 그대로 붙여 넣는 **마크다운 원문**이다(코드블록으로 감싸야 터미널에서 렌더링되지 않고 `-`·들여쓰기가 살아 있는 원문이 복사된다). 블록 아래에 `확인 필요` 목록을 붙인다: 확인 못 한 배포 여부, 비어 있는 URL·계정 정보, 첨부할 스크린샷 등.
5. 사용자가 원하면 `slack_send_message_draft` 로 슬랙 초안에 저장한다. **직접 전송(`slack_send_message`)은 사용자가 명시적으로 요청할 때만** 한다.

## 양식

### `배포` (기본)
```markdown
@담당자1 @담당자2 <기능/화면 이름>에 대해 운영서버 배포했습니다 확인 부탁드립니다.
다만, <실사용 제약이나 남은 일>.            ← 있을 때만
**바로가기**: <URL>                            ← 있을 때만
- **목적**
    - <어떤 문제가 있었는지>
    - <이번 배포로 무엇이 달라지는지>
- **추가사항**
    - <항목명>
        - <사용자·운영자 입장에서 바뀐 동작>
- **수정사항**
    - <항목명>
        - <무엇이 문제였고 어떻게 고쳤는지, 가능하면 전후 수치>
- **참고사항**
    - <다음 배포 예정, 담당자 결정 사항, 첨부 안내>
```
- `목적` 은 항상 넣는다. `추가사항`·`수정사항`·`참고사항` 은 해당 없으면 뺀다.
- `바로가기` 라벨과 1단 섹션 이름(`목적`·`추가사항`·`수정사항`·`참고사항`)은 굵게 쓴다(아래 '마크다운 규칙'의 굵게). URL 과 2·3단 내용은 굵게 하지 않는다.
- 결정이 필요한 쟁점이 남았으면 첫 문장을 "…배포했습니다 다만, 논의사항이 있어 논의사항도 확인 부탁드립니다." 로 바꾸고 끝에 `- **확인된 내용**` / `- **선택지**`(a. b. c. 와 각 장단점) / `- **논의가 필요한 점**` 을 붙인다. 이 섹션 이름도 굵게 쓴다.

### `공지`
```markdown
@channel
[태그] <한 줄 제목>              ← 태그는 [보안]·[공지] 등, 없으면 제목만

<무엇인지 1~2문장. 누가 어떻게 쓰는지, 결과물이 무엇인지>

- **바로가기**: <URL> (접근 정보는 따로 전달)
- 지금 상태: <운영 배포 완료, 시험 횟수 등>
- <영역>: <조치 내용>
- 첨부: <스크린샷 목록>

<영향 한 줄. 예: 사용자 쪽 영향은 없습니다.>
자세한 내용은 스레드에 정리했습니다.
```

### `결과`
```markdown
대표님 <무엇> 결과 공유드립니다

<기준·표본 한 줄. 예: 운영 DB 검증 사료 2,232건으로 비교했습니다.>
- <핵심 수치 결과>
- <해석·한계>

<제안 제목> (제안)
1. <구간/항목> (<전 → 후 수치>)
    - 문제: …
    - 방안: …

적용 순서 제안
1. …
```

### `보안`
```markdown
@channel
[보안] <프로젝트> <YYYY-MM-DD> 보안 점검 — <조치 완료 / 조치 중 / 새 조치 없음>

<이슈 n건을 대조했고 영향 있는 n건을 조치했습니다. 사용자 쪽 영향은 없습니다.>
**바로가기**: <노션 보안 보고서 URL>
- **영향 판정**
    - <이슈 이름 — 무엇을 당할 수 있는 결함인지>
        - <영향 있음 / 영향 가능 / 낮음> — <근거: 무엇이 해당됐고 밖에서 닿는지>
    - 그 밖 <n>건은 해당 없음(쓰지 않거나 이미 수정 버전)
- **조치**
    - <대상: 서버 / DB / 앱·의존성 / 이미지 / 개발 도구 / 절차>
        - <전 → 후 버전, 끊긴 시간, 취약점 건수 전 → 후>
- **확인**
    - <운영에서 다시 잰 값>
    - <운영 최종 테스트 범위와 판정>
- **남은 것**
    - <항목>
        - <왜 남았는지, 실제 위험이 어느 정도인지, 다음 확인일>
```
- 노션 보안 보고서의 절을 그대로 줄인 양식이다. 요약 문장 ← `0. 한 줄 요약`, `영향 판정` ← `1. 이슈별 영향 판정`, `조치` ← `조치 현황`·`5. 재발 방지`, `확인` ← `4. 검증 결과`·`4-1. 운영 최종 테스트`, `남은 것` ← `7. 남은 과제`. 자세한 내용은 `바로가기` 의 보고서가 맡으므로 글은 화면 하나에 들어오게 줄인다.
- **판정 용어는 보고서와 같은 것만** 쓴다(`영향 있음`·`영향 가능`·`낮음`·`해당 없음`). `확인 못 함` 은 `남은 것` 에 적는다.
- `영향 판정` 에는 `영향 있음`·`영향 가능` 을 전부, `낮음` 은 조치했거나 미룬 것만 적는다. 나머지는 "그 밖 n건" 한 줄로 묶는다. 새 이슈가 없으면 "기간 안에 새로 나온 해당 이슈 없음" 한 줄만 쓴다.
- **해당 없는 섹션은 뺀다** — 조치가 없으면 `조치`·`확인`, 남은 것이 없으면 `남은 것`. `영향 판정` 은 항상 넣는다.
- **제목 끝 결론** — 승인된 조치를 모두 운영에 반영했으면 `조치 완료`, 일부만 했거나 반영 중이면 `조치 중`, 오늘 한 조치가 없으면 `새 조치 없음`. 남은 것이 있는데 "조치가 필요 없다"고 쓰지 않는다.
- **`@channel` 은 조치를 했거나 `영향 있음`·`영향 가능` 이 있는 날만** 붙인다. 그 밖의 날은 뺀다(매일 전체 알림이 가지 않게 하기 위함).
- **프로젝트마다 글 하나, 글 하나당 코드블록 하나** — 새 조치가 없는 프로젝트들은 한 글로 묶고 제목에 이름을 나열한다.
- 요약 문장은 존댓말, 불릿은 전부 음슴체. `영향 판정` 의 "그 밖 n건" 줄과 `확인` 은 2단에 문장을 그대로 쓴다(말투 규칙의 "2단은 항목명만"의 예외).
- 보고서에 `6. 점검 중 정정한 내용` 이 있으면 `#보안-점검` 의 내 최근 글을 읽어(읽기만 함) 그 틀린 내용이 올라갔는지 확인하고, 올라갔으면 요약 문장 다음 줄에 "정정: <무엇이 틀렸고 실제는 무엇인지>" 를 한 줄 넣는다.
- 취약점은 "무엇을 당할 수 있는지"로 풀어 쓴다. 예: "리눅스 커널 결함(인터넷에서 서버를 멈추게 하거나 조종할 수 있는 결함)", "이미지(서버 프로그램 묶음)", "Debian(기반 운영체제)".
- 작업 중 사고나 서비스 중단이 있었으면 숨기지 않는다. 요약 문장의 사용자 영향과 `조치` 의 해당 항목에 시각·길이·영향·고친 절차를 적는다.

## 마크다운 규칙
- **리스트는 `-` 만** 쓴다. 2단은 4칸, 3단은 8칸 들여쓰기. 슬랙에 붙이면 `•`·`◦`·`▪︎` 로 바뀌므로 기호 문자를 직접 쓰지 않는다.
- 순서가 있는 항목(선택지, 적용 순서)은 `1.` 번호 리스트.
- 멘션은 `@이름`, 전체 알림은 `@channel`. `<@ID>`·`<!channel>` 같은 API 문법은 붙여 넣으면 글자 그대로 남으므로 쓰지 않는다.
- 링크는 URL 을 그대로 쓴다(슬랙이 자동으로 링크로 바꿈).
- **굵게는 정해진 라벨에만** 쓴다: `바로가기` 라벨, `보안` 양식의 1단 섹션 이름(`영향 판정`·`조치`·`확인`·`남은 것`), `배포` 양식의 1단 섹션 이름(`목적`·`추가사항`·`수정사항`·`참고사항`, 논의 섹션 `확인된 내용`·`선택지`·`논의가 필요한 점`). 그 밖의 문장·항목명·URL 에는 쓰지 않는다.
    - 굵게는 별표 두 개 `**목적**` 로 쓴다. 붙여 넣는 원문과 `slack_send_message_draft` 초안 저장 모두 같은 표기다. 별표 하나 `*목적*` 는 쓰지 않는다.
- 제목(`#`)·표는 쓰지 않는다. 기존 공유 글에 없는 형식이다.

## 말투 규칙
- **첫 문장·참고사항, 공지·결과 본문은 존댓말**(`~했습니다`, `~부탁드립니다`, `~예정입니다`).
- **목적·추가사항·수정사항 불릿은 음슴체**(`~함`, `~음`, `~됨`) 또는 명사형 종결. 마침표는 붙이지 않아도 된다.
- **2단은 항목명만**, 설명은 3단에 1~3줄.
- **비개발자 기준**: 코드·파일·함수 이름 대신 화면 이름과 동작으로 쓴다. 화면·버튼 이름은 '작은따옴표', 메뉴 경로는 `상품관리 > 판매 상품` 처럼 `>` 로 잇는다. 기술 용어는 괄호로 풀어 준다. 예: "안심번호(가상번호)", "사진 판독(AI가 라벨을 읽는 단계)".
- **구체 수치 우선**: "빨라짐" 대신 "480 KB → 184 KB, 판독 7.1초". 확인 못 한 수치는 쓰지 않는다.
- **결정 주체 표시**: 사용자·담당자가 정한 동작은 끝에 `(사용자 결정)`·`(담당자 결정)` 을 붙인다.
- **이모지 금지**. 사용자가 요청한 경우만 예외.
- 한 묶음은 화면 하나에 들어올 만큼. 사소한 리팩토링·테스트는 넣지 않거나 `참고사항` 한 줄로 끝낸다.

## 주의사항
- 운영 배포가 확인되지 않았으면 "운영서버 배포했습니다" 를 쓰지 않는다. "배포 예정입니다" 로 쓰고 `확인 필요` 에 적는다.
- 비밀번호·토큰·API 키는 텍스트에 넣지 않는다. 계정 정보는 "기존 비번 (대표님께 확인)" 처럼 위치만 안내한다.
- `보안` 글에는 서버 주소·자원 ID·계정명을 넣지 않는다. 버전과 건수, 끊긴 시간까지만 쓴다.
- 이 커맨드는 git 에 아무것도 커밋하지 않는다.

## 예시 (참고용)

```markdown
@담당자1 @담당자2 밀리크 주문조회 시스템에 대해 운영서버에 배포했습니다 확인 부탁드립니다.
다만, 현재 쿠팡에 등록한 제품이 없어 실 사용은 제품 등록 후 가능합니다.
**바로가기**: https://www.mealiq.co.kr/mypage
- **목적**
    - 고객이 쿠팡에서 밀리크 상품을 실제로 샀는지 확인할 방법이 없어 추천 → 구매의향 → 실구매 전환을 볼 수 없었음.
    - 그래서 고객이 쿠팡 주문번호를 입력하면 서버가 쿠팡 판매자 API로 주문을 검증해 실구매로 기록하는 방식으로 설계·구현함
```
