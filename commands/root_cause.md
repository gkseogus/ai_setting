## 실행 순서

### 1. Triage 보고 (사용자 동의 게이트)
- 현재 에러 / 버그를 한 문장으로 요약.
- **"뿌리 뽑기 / 싹 자르기"** 중 어느 쪽이 맞는지 근거와 함께 보고.
- 사용자 동의를 받은 뒤 다음 단계로. 동의 없이 코드 수정 금지.

### 2. 근본 원인 추적 (근본 처리로 결정된 경우)
- **재현**: 에러 재현 조건 확인. 재현 불가 시 그 사실과 가설 명시.
- **5 Whys**: 각 Why마다 코드 / 로그 / DB / 응답 등 증거 첨부.
- **흐름 추적**: 트리거(증상 지점)와 진짜 원인(증상을 만든 지점)을 분리.
- **유사 패턴 grep**: 같은 코드 패턴 / 같은 실수가 다른 곳에 있는지 후보 나열.
- "가설"이 아니라 **증거 기반 결론**으로 정리.

### 3. 수정
- 근본 원인 지점을 직접 수정. 회피 / 우회 / 방어 코드만 추가 금지.
- 2단계에서 찾은 **유사 패턴도 함께 수정**.
- 표면 처리가 불가피하면 `# TODO(root-cause): <원인 가설 + 후속 작업>` 주석 + 사용자에게 명시 보고.

### 4. 검증 (반드시 4개 모두 수행)
1. **증상 재현 불가 확인**: 원래 에러 조건으로 실제 동작시켜 발생 안 함을 확인 (curl / 스크립트 / 브라우저 / 테스트).
2. **유사 패턴 확인**: 2단계 4번에서 찾은 같은 패턴들도 같은 증상 없는지 확인.
3. **회귀 확인**: 원래 잘 되던 정상 흐름이 깨지지 않는지 최소 1개 직접 확인.
4. **재발 방지 테스트**: 자동화 가능하면 테스트 추가.

> 타입체크 / 빌드 / lint 통과만으로는 검증이 아니다. **실제 동작 관찰** 필수.

### 5. 보고 (아래 5개 항목 그대로 출력)
- **처리 방식**: 근본 / 표면
- **근본 원인**: 한 문장 요약 (증거 기반)
- **수정 범위**: `파일:라인` + 변경 요지, 함께 수정한 유사 패턴
- **검증 방법**: 실제로 실행한 명령 / 동작과 그 결과
- **잔여 리스크 / 후속 작업**: 있으면 명시, 없으면 "없음"

## 금지 사항
- "고친 것 같습니다" / "아마 될 것입니다" 같은 미검증 보고 금지.
- 검증 4단계 중 하나라도 빠뜨린 채 "끝났다" 보고 금지.
- 에러 메시지만 보고 `try/except`, `if` 가드로 우회하면서 "수정" 이라 칭하는 것 금지.
- 표면 처리하면서 사용자에게 알리지 않는 것 금지.
- 근본 원인을 모르는 채로 "재시작하면 됩니다" 식으로 넘기는 것 금지.
